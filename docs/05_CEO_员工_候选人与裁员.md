# 05｜公司与CEO创建、员工候选人、聘用、成长与裁员

## 5.1 随机公司名

资源配置`companyNamePrefixes[]`、`industrySuffixes`、`companyNameEndings[]`，至少30个安全趣味前缀，如“今天也盈利”“老板有点忙”“一条咸鱼”“明天上市吗”“亿点点梦想”等；避免真实知名商标、低俗词或误导“官方”“国企”等词。`rollCompanyNames(industry, count=3)`在界面上免费刷新，不消耗经营年份和现金；每次刷新最少3个不同候选，使用**非财务 RNG 流**，不可因点刷新而改变未来市场事件。

自定义名称：去首尾空白、统一全角空格、限制建议2—20个中文字形等价值长度（最终按Cocos字体可视宽度验证）、禁止全空白/控制字符、敏感词过滤；屏蔽不可控富文本或渲染标签输入。显示使用纯Label文本，绝不通过HTML解释。用统一结果错误码`INVALID_NAME`反馈。

## 5.2 CEO

创建页面：姓名自定义或随机、性格三选一（进取/稳健/亲和），并列展示三项能力50/50/50，解释不同成长偏向：

| 性格 | 每完整年度成长 | 行为风格文案 |
|---|---|---|
| 进取 | 商业+2，管理+1，财务+1 | 擅长开发市场 |
| 稳健 | 商业+1，管理+1，财务+2 | 擅长资金管理 |
| 亲和 | 商业+1，管理+2，财务+1 | 擅长团队协作 |

能力上限100；每个年度关账后增长，不得因为重新查看年报增加属性。CEO名称与公司名称都只属于当前run，重开时全部清空。

## 5.3 员工与岗位

每名员工：`id,姓名,头像资源ID,专业能力0..100,成长潜力0..100,团队协作0..100,性格[进取/稳健/协作],月工资元,部门ID,聘用/生效月份,状态`。岗位不单独建立复杂职业系统；玩家在业务部或支持部门点击招聘时，候选就为那个部门生成。头像使用可复用卡片插画而非每人独立制作昂贵资源。

### 候选生成算法（必须可复现）

- 对每个部门Offer使用`hash(runSeed,deptId,offerSequence)`衍生独立RNG，姓名/性格/属性和工资固定；刷新后`offerSequence+1`，旧Offer全部失效。
- 3人至少体现“高能力”“高潜力”“性价比”三种倾向，基准属性：
  - A 即战力：skill 75~90、potential 45~75、teamwork 45~85、salary 6200~8000。
  - B 潜力股：skill 50~70、potential 80~98、teamwork 50~90、salary 5000~7200。
  - C 经济型：skill 45~72、potential 50~85、teamwork 55~90、salary 4000~5800。
- 工资限制4,000~8,000。三个候选不能完全相同；优先在界面解释差异，不暗示某候选“保证高收益”。
- 招聘费基线=月薪；HR折扣只对**支付当时已经生效**的HR部门影响；不得事后退款。
- 经营模式自动招聘候选也使用可复现Offer并生成招聘操作日志；玩家手动刷新不会影响年度事件随机序列。

## 5.4 招聘：明确状态机

`AVAILABLE_OFFER → PREVIEW → CONFIRMING → HIRED/REJECTED`。

手动招聘：
1. 在具体部门点“招聘”，生成或读取当前未过期Offer（3候选）。
2. 点候选卡显示`立即支付招聘费、预计年薪、产能/部门贡献预测、余额`。
3. 点击录用后重新校验`offerId+candidateId+departmentId+runId+revision`、现金≥招聘费、该人未被录用。
4. 同一`commandId`第二次调用返回前次结果，不再扣费；不同命令试图录用已录用候选报错。
5. 费用在点击确认时从现金立即扣除，登记唯一`entryId`；在职与工资从**下一个完整模拟月**生效。首次2名员工为启动前特殊情况：第1月生效、费计入首年第1月。
6. 提交成功显示员工卡与工资变化；提交失败UI保持原Offer，不假装成功。

### 录用在时钟/离线边界

所有命令进入同一个串行`GameMutationLock`；先完成待模拟月份落盘，再提交录用，避免“一月月底同一人收了两次工资”。若玩家位于年度最后一天、首聘阶段尚未完成，按上面的生效月规则走；UI“本年度预计工资”需解释只计剩余月份。

## 5.5 员工年成长

年末对在职满一个完整年度的员工：`delta = max(1,round(potential/30))`，专业能力`min(100,skill+delta)`；任职不足一年者可按`满12个月才增长`处理（第一版统一规则）。

成长潜力本身不增长、薪资不自动上涨、性格不可在本阶段修改；员工离职后不保留无限历史。所有人才成长只在已完成年结中执行一次。

## 5.6 裁员

裁员只允许玩家主动触发。`GET preview`必须提供：姓名、部门、月薪、已任职年数、补偿月数、补偿金额、次年工资节约估算、预计产能/部门效益损失、裁后现金。

公式：`在职年数 = floor(在职月数/12)`，`补偿月数 = min(3,max(1,ceil(在职年数/2)))`，补偿=月薪×补偿月数。例：已任职3年、月薪8,000，赔偿16,000。实际劳动法规因地区与合同不同，本公式**仅游戏机制**。

按钮顺序：员工详情→“裁员”→“确认补偿说明”→确认；Token有效60秒，确认时再次计算金额并验证是否变化；如预览与提交状态不一致则要求重新确认。现金不足报`INSUFFICIENT_CASH`；**不得负现金，不允许在未经确认的后台自动裁员。**

确认立即支付赔偿并计入本期费用；员工本期剩余月份/下月状态按统一次月生效规则。防重复扣费/状态转换：`ACTIVE→PENDING_DISMISSAL→DISMISSED`；已处于待裁员者不能再申请裁员；到生效月份移除产能和工资。

## 5.7 自动招聘与手工干预关系

- 仅当`department.staffingMode=AUTO`时允许自动聘人；`LOCKED`时守住目标人数但不会自动补员，UI说明。
- 自动招聘最低现金留存覆盖预计未来6个月刚性费；不能让自动招聘推动公司进入立刻无法支付工资的危机。
- 自动招聘每个内部月最多**1人/公司**（防膨胀），每经营年度建议最多**3人**（首轮平衡值），按预计收益排序。
- 自动不裁员、不解雇新人、不建立新部门、不花钱扩张业务资产。
- 手动招聘不受每月自动招聘限制，但须现金足够；若业务需求不足提醒“人手可能闲置”，不禁止玩家选择。

## 5.8 关键测试

- 反复点击录用10次只扣一次招聘费。
- 刷新候选后用旧candidateId提交应返回`OFFER_EXPIRED`。
- 同员工重复裁员、现金不足裁员、裁员前后跨月、点击确认时额外发生年结、手机杀进程后重试。
- 潜力高员工五年后能力成长超过低潜员工的一部分情形；但并非所有情况都如此。
- 姓名长文本、emoji、特殊字符、敏感词与空值；不溢出UI、不执行标签。
- 多次重开后名字与属性、初始招聘数和现金正确清零。
