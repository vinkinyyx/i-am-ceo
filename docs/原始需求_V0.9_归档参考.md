# 《我是CEO》第一阶段 MVP 需求、数值基线与 TapTap 适配 V0.9

> 状态：**第一阶段需求范围已收敛，新增主动关闭并重新创业、首次启动交互引导、TapTap 小游戏发布适配；平衡经营（B）数值仍为首轮测试建议。**  
> 原则：单公司、单主营业务、多个部门、个体员工招聘、轻量2D竖屏、按年经营、可加速与离线挂机、可以亏损并恢复经营。**不引入第二阶段机制。**

## 1. 产品目标和明确边界

**玩家目标**：从30万元初始资本创业，自定义公司及CEO，选择一个主营行业，比较招聘候选员工，建立主营业务与成本/支持部门，经过经营调整实现连续3个年度盈利，并持续积累资产、提高本地排行榜名次。达标后继续自由经营，不强制结束。

**第一阶段必须实现**
1. 创业：趣味随机公司名（刷新多个候选）/自定义公司名；自定义/随机CEO姓名；选择CEO性格。
2. 单一主营行业：贸易、软件科技、企业服务三选一；**创建后不可在第一阶段切换或新增主营行业**。
3. 员工：每次招聘展示3名可比较候选人（能力、成长潜力、协作、性格、薪资、一次性招聘成本）；手动录用、自动招募；员工逐年成长；主动裁员并支付补偿。
4. 部门：主营业务部 + 人力资源、采购、市场、客服、财务五种支持部门；自主创建/配置人员/暂停招聘；成本与收益可解释。
5. 财务：现金、收入、直接成本、业务运营费、员工工资、招聘费、裁员补偿、部门设立费、利润；简化经营资产与总资产；按年生成报告。
6. 经营：默认自动，玩家随时手动介入；1×/2×/5×加速、暂停、离线结算、轻微随机事件；年度亏损不直接破产。
7. 本地模拟排行榜：总资产榜与经营年限榜；不接入真实玩家在线排名。
8. 竖屏2D交互：以点击、滚动和卡片展开为主，无角色走路和复杂动画。
9. **关闭公司并重开**：游戏内清除本轮全部经营数据，再次进入公司/CEO创建；与TapTap平台身份及隐私账号注销分离。
10. **首次进入操作引导**：以引导层逐步教学，允许跳过、重新回看，不要求玩家观看演示动画。
11. **TapTap 发布适配**：目标为 TapTap 普通小游戏（非传统APK），将资质、打包、平台登录、触控、存储、隐私和验收列入第一阶段。

**明确不在第一阶段开发**：跨行业、多主营业务、子公司、集团、并购、上市、贷款及股权、复杂税务与会计、真实竞对经营AI、实时多人排行榜、生产线/库存明细、员工技能树、人物关系、复杂随机事件链、IT与法务等更多部门、3D办公室及重动画。

## 2. 经营节奏和新手体验

### 2.1 计时
- **一个完整经营周期 = 游戏内一年**，内部以12个月依次结算；玩家不需要逐月操作。
- 在线：1× = 5分钟/年，2× = 2分30秒/年，5× = 1分钟/年；支持暂停。
- 离线：累计每8小时现实时间模拟1游戏年，按比例结算；单次结算最多3游戏年；首次新手引导暂停计时。
- 时间相关的结算以游戏内月份为准，不以设备帧率为准。离线不能触发玩家未授权的重大投资、裁员或跨范围动作。
- 同一离线时间段只结算一次；读档、切换加速、频繁进入后台不得重复领取收益。

### 2.2 前5年引导（引导内容，而非强制事件/强制行为）
| 时间 | 玩家学到什么 | 玩家看到的操作/反馈 | 合格条件 |
|---|---|---|---|
| 创业前 | 公司与CEO设定 | 随机或自定义名称、行业3选1、CEO姓名/性格、初始招聘2人 | 5个步骤内完成创建，数据存档 |
| 第1年 | 收入≠利润 | 观察订单、产能、工资、直接成本、年度结果 | 可解释年利润构成 |
| 第2年 | 招人有成本 | 展示3名候选，比较高能力/高潜力/低工资，支持暂不招聘 | 可拒绝招聘；自动模式不会盲目扩员 |
| 第3年 | 部门有投入产出 | 推荐适合行业的支持部门，展示预计节省额/新增工资/净贡献 | 可设或不设，可用数据解释选择 |
| 第4年 | 经营存在风险 | 轻度波动或经营建议，体验调整人员/部门以应对压力 | 亏损时可继续经营 |
| 第5年 | 稳定盈利与排名 | 年度趋势、资产榜/年限榜、连续盈利目标 | 连续3年盈利记录；达成后自由经营 |

**新手引导建议**：首屏只指导一个动作；不遮盖现金与利润；所有教程可跳过、可从帮助入口回看。首次进入的逐步点击式教学以第11节详细流程为准；前5年的引导属于后续可选提醒，不强制剧情。

## 3. B平衡难度：经济参数建议

### 3.1 全局初始参数
| 参数 | 测试初值 | 备注 |
|---|---:|---|
| 创业注入资本 / 初始现金 | 300,000元 | 创业资本不属于营业收入或利润 |
| 初始主营业务数 | 1项 | 不可新增第二项 |
| 初始员工 | 玩家手动招聘2人 + CEO | CEO不领固定工资（第一阶段简化） |
| 普通员工月薪 | 4,000—8,000元 | 候选差异化，参考算例使用行业均薪 |
| 一次性招聘费 | 候选人的1个月工资 | 录用时扣现金，计入当期费用 |
| 裁员补偿 | 月薪×min(3,max(1,ceil(在职年数/2))) | 游戏参数；**不对应现实劳动法**。执行前必须二次确认 |
| 新设支持部门费用 | 10,000元/部门 | 一次性经营费用，支付后才能启用 |
| 支持部门初始人数 | 0 | 部门存在但无员工时不产生节约/获客收益 |
| 部门/员工总数上限 | 不设业务性硬上限 | 按需求、资金和设备性能控制；UI使用分组及列表 |
| 阶段性目标 | 连续3年经营利润>0 | 不强制结束存档 |
| 事件概率 | 每游戏年25%出现至多1个轻度事件 | 数值取值见风险章节 |

### 3.2 行业基线（首年中性CEO、标准招聘、无事件，单位：万元）

统一收入公式：

`实际营业额 = min(潜在订单额 × 获客系数, 交付产能) × 成交完成率`

第一年基准的获客系数及成交完成率均视为1.0；后续由CEO、市场部、客服和事件小幅调整。

统一费用计算：

`年度利润 = 实际营业额 - 直接成本 - 业务运营费用 - 固定管理费用 - 全部员工工资 - 招聘费 - 裁员补偿 - 部门设立费 - 事件净损失 - 当期折旧`

第一年**未扩张业务资产，折旧=0**。行业参数：

| 行业 | 潜在订单额 | 2人初始交付产能 | 直接成本率 | 业务运营费率 | 2人参考月薪 | 固定管理费/年 |
|---|---:|---:|---:|---:|---:|---:|
| 电商贸易 | 72 | 80 | 60% | 10% | 每人5,000元 | 4.8 |
| 软件科技 | 40 | 50 | 25% | 12% | 每人6,500元 | 4.8 |
| 企业服务 | 45 | 56 | 35% | 10% | 每人6,000元 | 4.8 |

据此首年利润：
- **贸易**：72 − 43.2 − 7.2 − 12 − 1（两人招聘费）− 4.8 = **3.8万元**，期末现金33.8万元。
- **软件**：40 − 10 − 4.8 − 15.6 − 1.3 − 4.8 = **3.5万元**，期末现金33.5万元。
- **服务**：45 − 15.75 − 4.5 − 14.4 − 1.2 − 4.8 = **4.35万元**，期末现金34.35万元。

这些是**基准样本**，不是保底收益。更贵的候选人、较低业务能力、部门过早扩建或负面事件都可导致亏损。首年不要默认强制为正。

### 3.3 产能、CEO与员工成长（最简机制）

- 员工保存 `专业能力(0—100)、成长潜力(0—100)、团队协作(0—100)、性格标签、月薪、在职年数`。
- 每人当年参考产能 = `行业参考单人产能 × (0.7 + 专业能力/200)`。贸易单人参考40万元、软件25万元、企业服务28万元；60能力对应1倍参考产能。
- 部门协作系数 = `clamp(1+(部门员工平均协作-50)/500, 0.9, 1.1)`；CEO管理加成为 `clamp(1+(CEO管理能力-50)/500, 0.9, 1.1)`。
- 主营业务交付产能 = `业务员工参考产能之和 × 协作系数 × CEO管理加成`。员工越多不保证订单越多，必须有市场需求。
- 员工每完整工作1个游戏年，专业能力增加 `max(1,round(成长潜力/30))` 点，上限100；招聘成本不会重复发生。
- CEO三个能力：商业、管理、财务，初始总点数150；三种性格各偏重一个成长方向，非偏重能力每年+1、偏重能力每年+2，上限100。CEO商业影响获客（围绕基础1.0上下小幅浮动）；财务对可控运营费提供小幅改善，不直接凭空增加现金。
- 初始员工能力属性影响上述基线；为了算例可复现，贸易样例的员工能力为60、协作50、CEO管理50。

### 3.4 五个支持部门的作用与限制
| 部门 | 简化主要效果 | 重要限制 |
|---|---|---|
| 人力资源 | 招聘费折扣、轻微减少员工流失风险 | 无招聘时可能短期亏本 |
| 采购 | 贸易直接成本节省，基准1名合格员工最高8%—12% | 只针对适用采购支出，且有上限；软件/服务作用较低 |
| 市场 | 增加潜在订单和成交机会 | 不突破交付产能；自身工资仍是费用 |
| 客服 | 减少退货/售后费用，改善次年客户需求 | 作用限定在售后相关费用，不重复节约全部成本 |
| 财务 | 降低可控管理费用、改善经营风险提示 | 不制造虚假营业收入，无贷款系统 |

计算顺序：先计算行业基线成本，再对**相应成本项**应用部门节约，最后加上部门工资、设立费及招聘费。部门效益受服务规模/员工能力约束，不能简单无限叠加，最低成本不得为负。

**支持部门常态员工参考工资**由生成的候选人决定，通常在5,000元/月左右。例如贸易当年采购原始支出96万元，采购部节省8%即7.68万元；一名员工月薪5,000元（年6万元），招聘费0.5万、设立费1万，则设立当年**净贡献+0.18万元**。如果采购支出只有43.2万，该部门同样配置当年就会亏损。该差异必须在界面中提示。

### 3.5 业务成长与经营策略
- 默认**稳健经营**，可改为**扩张**或**利润优先**；三种策略改变自动招聘阈值、可用年度投入预算及现金安全边界，而不是直接给予固定利润奖励。
- 市场需求随年份平缓增长并受事件影响（测试建议正常年度增长8%—12%）；不是保底，部分年度可下降。
- 业务扩张投入只用于提升营业能力/产能上限，不解锁新行业；投入被记录为简化业务资产而不是全部计入当年费用。可先只提供一个“扩大业务能力”按钮和预计增量，避免设计生产线。
- 若引入业务资产折旧：从**次年起**按未折旧业务资产账面余额的10%计提，扣减年度利润与资产账面价值，不重复扣现金；首年不扩张，因此首年算例不受影响。

## 4. 招聘、自动管理与裁员

### 4.1 员工招募
1. 点击“招聘”进入候选列表，**每次展示3名**不同特征的候选人。
2. 显示姓名、头像、性格、专业能力、成长潜力、协作、工资和一次性招聘费；支持并排重点参数比较。
3. 选择候选人和目标部门后显示：招聘费、预计年工资、对该部门产能/效益的预估影响。
4. 点击“录用”时校验现金和岗位状态，成功后一次性扣招聘费，下一内部月份开始计薪和生效。
5. 候选人刷新可以免费（第一阶段），但必须保持明确的候选ID，防止刷新后误录用不同人。

### 4.2 自动招聘模式
- 每个部门支持 `自动` / `手动锁定`；公司默认自动经营，**首批两名员工由玩家在引导中亲自选择**。
- 自动招聘仅在预计需求显著超过可交付能力、增员预计能改善中期收益且满足现金安全线时触发；候选评分兼顾能力、潜力、薪资及性格适配。
- 自动招聘不得超出当年设定的人力支出预算；玩家锁定的部门人数不得被自动模式修改。
- 自动模式在现金不足时暂停招聘；**第一阶段不允许自动裁员**，避免离线发生未经同意的补偿与裁员。

### 4.3 裁员
- 选择具体员工→查看月薪、任职年数、预计赔偿、次年节约工资及部门影响→二次确认。
- 实际裁员从下一内部月份生效，补偿为一次性费用及现金流出；不得重复扣补偿。
- 人手减少后需重新计算产能和支持部门效果；允许裁员后业务收入下降。
- 不允许负现金支付补偿。现金不足时提示无法裁员或先通过经营恢复现金；不暗中生成贷款。

## 5. 年度财务、资产排名及失败保护

### 5.1 核算
- 以12个月内部小账本逐笔模拟与累加，年度报告汇总；员工入职/离职从下个月起影响工资。
- 现金变化 = **收现营业收入 − 付现直接成本 − 付现运营成本 − 工资 − 招聘费 − 裁员补偿 − 部门费 − 资本性业务扩张投入 − 事件现金损失**。若有非现金折旧，不得重复从现金扣除。
- 利润不等于现金变化：扩张资产投入是现金流出，但不是一次性当年经营费用；折旧影响利润不影响当期现金。
- 总资产（简化）= 现金 + 未折旧业务资产；无贷款系统，暂不计算负债与股权估值。创业资本增加资产但不计为营业收入。
- 排行榜展示 `总资产` 与 `经营年限` 两个独立榜，虚拟企业随模拟年份演变；**不得用累计营业额或公司估值冒充总资产**。

### 5.2 亏损与经营危机
- 年利润<0只显示“年度亏损”，不触发破产、不重置存档。
- 可用现金低于未来6个月刚性费用时：显示黄色经营风险；关闭高风险自动招聘/扩张，继续经营。
- 现金预计无法覆盖下一个月必要支出时：进入“经营困难”状态，停止新增开支并弹出简易重整建议；可手动暂停支持部门、削减预算或等待可覆盖费用的经营收入。
- 为避免无现金又无法裁员的死锁，第一阶段提供**仅一次**“CEO追加经营资金10万元”重整选项：计入新投入资本/现金，不算营业收入和利润；已使用则不可再领。
- 不自动删除存档、不因单次亏损失败；可在恢复经营后继续累计经营年份。此处不实现融资、银行、借款或正式破产流程。

### 5.3 小幅随机事件（5种足够）
- 新订单增长、订单减少、供应成本上涨、员工意外离职、一次性设备/售后损失。
- 每年最多触发1个；建议总概率25%，影响约为本年正常营收或相关成本的5%—12%，不得造成超出上限的不可逆连锁打击。
- 事件在年度报告中解释实际金额；离线按同样概率和效果结算，但严禁自动执行重大玩家决策。

## 6. 四个主界面及导航

基准适配：竖屏 9:16，设计参考宽360—390逻辑像素。触摸目标建议≥44×44逻辑像素，正文和财务数字有足够对比，不依赖颜色区分盈亏。无需复杂动画，只保留轻微点击反馈、数字过渡与弹窗反馈。

| 底部Tab | 首屏信息 | 二级交互 |
|---|---|---|
| **公司** | 公司名、CEO、经营第N年、年进度、现金、预计年营收/利润、暂停与倍速、经营风险提醒 | 创建信息、CEO属性、年度报告、经营策略、业务扩张投入 |
| **部门** | 主营业务部 + 已开设支持部门卡片（人数/年成本/效益） | 创建部门、配置人员、部门自动/手动、查看投入产出 |
| **人才** | 员工总数、工资总额、候选人入口、部门筛选、员工列表 | 3选1招聘、候选对比、裁员确认、员工成长明细 |
| **排行** | 总资产榜/经营年限榜、我方名次与变化 | 查看模拟企业摘要、历年趋势 |

**年度报告不设第五个Tab**：在公司首页年度结算后弹出摘要，也可从“历史报告”进入。创建公司是首次启动流程，不占底部菜单。

### 必要界面状态
- 首次启动：公司/CEO设定与2人招聘，默认暂停计时；跳过说明不跳过必要输入。
- 正常经营：计时、年度进度条、估算年利润，点击可进部门/人才。
- 年度结算：可关闭摘要，历史报告持久存储。
- 离线回归：显示经过的游戏年度、收入、利润、现金变动、事件及是否因保护而暂停。
- 资金紧张：黄色提示并说明原因/可执行操作；不阻塞查看数据。
- 数据为空：未建部门/无候选人/未上榜均有明确空状态。

不自建业务账号、不做跨设备云同步和真实玩家在线排行；第一版经营存档使用平台本地持久化。**TapTap小游戏登录/认证属于单独的平台适配义务**：如采用`tap.login`的`code2Session`校验流程，需由受信任服务端承接，不将会话密钥下发客户端；不能将“没有业务服务器”理解成“可以跳过平台登录要求”。

### 模拟执行顺序与幂等要求
1. 恢复存档，判断待推进的游戏内月份。
2. 按固定随机种子与月份编号决定需求变化/随机事件。
3. 执行自动决策（不得覆盖手动锁定与重大授权边界）。
4. 计算当期需求、交付产能、实际营收和各项费用。
5. 记账（招聘费/裁员补偿/设立费只记录一次），更新现金与资产。
6. 月末更新员工成长、部门收益及风险状态；每12个月生成年度报告并校验利润/现金勾稽。
7. 原子保存 `lastSimulatedMonth`，保证同一月份无法重复结算或重复领取离线收入。

## 10. 首轮平衡测试指标（开发后观测，不是玩家要完成的硬门槛）
- 无重大事件、正常招聘策略下，首年盈利应为**小额盈利或轻微亏损**；不能无脑高速增收。
- 同样开局进行10组不同候选员工/部门选择，应该出现不同利润和现金曲线；单一最优操作不能主导全部玩法。
- “提前创建部门”可以亏损，“在合适业务规模创建部门”能带来净收益。
- 自动经营应避免在现金警戒线以下继续大量招聘；手动违规操作仍可产生损失。
- 玩家理解主营业务、招聘、部门效益、年度利润及排行榜的流程应尽可能不依赖长篇教程。


## 11. 主动关闭公司并重新创业（新增，P0）

### 11.1 用户入口与操作
- 从 **公司首页 → 设置 → 关闭公司并重新开始** 进入。不得在首页设置一键误触入口。
- 第一次点击展示数据清单与不可恢复提示；玩家必须再次点击明确的红色确认按钮才执行。取消后不做任何修改。
- “公司关闭”是玩家主动结束本轮经营，不是现实破产机制、不是注销TapTap账号、不是游戏下架。
- 关闭成功后进入首次创建公司页面：重新选择随机/自定义公司名、CEO姓名/性格、主营行业和首批员工；重新领取**一次**初始30万元创业资金。
- 关闭后立即重进或离线回归都不得恢复原公司；旧公司经营产生的剩余离线收益不能转入新公司。

### 11.2 清零的数据范围

| 类别 | 重置行为 |
|---|---|
| 公司 | 名称、行业、创立年、资产、现金、业务规模、经营策略清零 |
| CEO | 名字、性格、成长属性与经营年数清零 |
| 人才 | 所有候选队列、录用员工、员工成长、工资、招聘及裁员状态清零 |
| 部门 | 全部部门、人员配置、自动策略、投入和部门历史清零 |
| 财务 | 月/年报表、事件、亏损年数、盈利目标进度清零 |
| 排名 | 本轮公司成绩从本地模拟排行榜中移除；模拟企业回到新一轮初始状态 |
| 时间与挂机 | 上次在线时间、已结算离线时间、水位标识、随机种子清零 |
| 新手引导 | 新一轮恢复首次创建及可选操作指引 |
| 平台身份 | **不清除/注销** TapTap平台账号或法定义务下留存的必要合规记录 |

### 11.3 重置技术规则（禁止旧档复活）
1. 运行前将`saveId/runId`与`resetGeneration`作为本轮经营唯一标识；所有定时器、后台结算任务、排行计算、缓存刷新都携带该标识。
2. 二次确认后先暂停经营时钟，阻止新的经营写入；将重置标记写入持久化，再清除全部旧经营数据，创建空白“待创建”状态。
3. 新公司必须使用全新`runId`、独立随机种子与零离线结算水位；旧经营事务迟到时因`runId`不匹配而被丢弃。
4. 本地写入失败不得显示“成功重置”；重新进入时检测到未完成的重置，应继续完成清理，不得自动加载旧公司。
5. **MVP仅使用本地经营存档**。若未来开通TapTap云档，重置必须同步删除云端经营档（官方`deleteArchive`），并在离线或云删除失败时防止旧云档重新覆盖新公司；不能声称旧云档已删除而实际仍存在。
6. 重置经营档与个人信息删除、TapTap账号注销分离。隐私政策、认证与法规需要保留的记录按适用规则处理。

## 12. 首次进入操作指引（新增，P0）

### 12.1 首次进入顺序

`启动页面 → 平台必要告知/隐私处理 → 登录/可用环境确认 → 公司创建 → CEO创建 → 招聘首批员工 → 经营首页交互引导 → 开始经营 → 首次年度报告提示`

> 只有首次新公司进入或“重新开始”后默认展示完整指引；中途退出后按已完成步骤恢复，不能强制重播。登录、隐私告知不属于可跳过的玩法教学。

### 12.2 六步可点击引导

| 步骤 | UI突出位置 | 玩家操作 | 成功反馈 |
|---|---|---|---|
| T01 创办企业 | 公司名称输入区和随机刷新 | 选择或输入名称 | 显示正式公司名，下一步按钮可点 |
| T02 CEO设定 | CEO姓名/性格卡片 | 选择姓名及性格 | 属性差异说明一行即可 |
| T03 招聘员工 | 三位候选人卡片 | 比较并录用首批2人 | 即时展示工资与招聘费用变化 |
| T04 认识经营首页 | 现金、年度收入、利润三个指标 | 依次点选“？”信息提示 | 展示收入/利润/现金的简短解释 |
| T05 开始经营 | 经营状态与加速按钮 | 点击“开始经营” | 年度进度开始变化，可切换倍速 |
| T06 读懂结算 | 首次年度报告（第1年结束时） | 查看年利润、现金变化及经营建议 | 可以关闭报告继续自由经营 |

**交互规范**：
- 单屏只展示一个高亮操作目标；说明文案尽量不超过2行，优先就地提示而非教程全屏长文。
- 可跳过教学说明，但公司基本信息和首批员工等正式经营必需步骤仍需完成；帮助入口可随时“重新查看操作指引”。
- 教学期间经营时钟暂停；首次年度报告到达时才展示T06，不在创建后直接模拟虚假结算。
- 所有按钮适合手指点击，触摸热区建议不小于44×44逻辑像素；适配安全区、刘海屏和字体缩放条件；不依赖声音或复杂动画完成教学。
- 显示哪一步、步骤是否完成保存在经营存档内。重建公司后清零，而重新启动既有公司不重置。

### 12.3 文案示例
- 首页：`欢迎成为CEO！先为公司取个名字。`
- 招聘：`能力高不一定最划算，记得比较工资与成长潜力。`
- 年度收入：`这是公司一年卖出了多少业务，不是你真正赚到的钱。`
- 年度利润：`扣除采购、工资和经营费用后，才得到利润。`
- 首年报告：`今年赚钱了吗？看看员工工资和部门费用。`
- 教学出口：`跳过指引` / `稍后在设置中重新查看`

## 13. TapTap 发布策略与官方规则（新增，第一阶段）

### 13.1 平台形态选择
- **目标发行形态**：TapTap「普通小游戏」（即点即玩）；不把Android APK作为第一版必交物。TapTap同时支持普通小游戏与H5小游戏，本次只定一种以避免双适配。
- **技术建议**：Cocos Creator **3.8.x及以上** + TypeScript，以UI卡片为主。使用TapTap官方`tap-minigame-ts`适配插件和构建流程。官方文档给出的工作流为“选择微信小游戏构建 → 勾选转换为Tap小游戏 → 填写Tap AppID”，最终产物通常为`build/TapBuild/game.zip`。以开发环境实测为准。
- 普通小游戏环境**不是浏览器**，不提供原生BOM/DOM；禁止直接把依赖`document/window/localStorage`的普通网页打包就当作合格小游戏。游戏业务逻辑与平台接口通过适配器解耦。
- **第一阶段不做**：微信小游戏双端支持、传统APK、真实玩家排行、付费内购、广告商业化、内购服务端、多人联机。可预留抽象接口，但不实施功能。

### 13.2 上架和资质清单（以提交时的最新后台及官方审核为最终准绳）

| 事项 | 具体设计/交付要求 | 状态 |
|---|---|---|
| 开发者主体 | 需完成TapTap认证开发者入驻；个人/企业按自身资质申请，未认证开发者无法正式提审 | 上架前必须完成 |
| 游戏创建 | 创建游戏时“游玩提供方式”选择小游戏，获得唯一游戏ID | 上架准备 |
| 备案 | **普通小游戏正式上架前完成小游戏前置备案**；官方提供一站式前置备案流程，需准备身份及游戏内容材料 | 上架前必须完成 |
| 版号/收费 | 当前官方小游戏指引：**不含内购小游戏无需提交版号**；第一阶段不提供内购与充值，避免付费资质路径 | 按当前规则设计，提交前复核 |
| 防沉迷 | 单独以“小游戏”游玩方式发布，官方指引说明依托平台防沉迷体系；不代表可绕过平台登录或隐私要求 | 联调验收 |
| 隐私 | 启动流程设置隐私政策入口和必要的数据处理告知；仅收集最少数据，不请求通讯录、定位、相册等无关权限 | 必须实现 |
| 内容安全 | 预设随机公司名不得侵犯商标/包含低俗词；自定义公司名/CEO名需长度限制及文本过滤；若未来公开展示用户命名须额外审核与申诉机制 | 必须实现 |
| 素材权利 | 自制或许可清晰的美术、字体、音频；保留许可证/授权证据；禁止擅用实际企业商标 | 必须实现 |
| 性能与包体 | 用官方插件打包合格ZIP，首包控制在官方限制内（建议目标≤60MB），文字和小图标优先，不放大型视频 | 构建验收 |
| 审核测试 | 上传开发包、自动化检查、Android/iOS的TapTap真机扫码测试，验证启动、触摸、存档、重开与离线 | 提审前 |
| 发布状态 | 完善商店详情和资质后再提交“正式上线（试玩版）”审核；正式游玩以平台审核结果为准 | 提审阶段 |

**说明**：官方资料中“完整游戏正式上线”“开放试玩”“小游戏正式上线（试玩版）”命名涉及不同发布路径；第一阶段仅以小游戏后台实际可选状态进行提审，不能误将传统APK资质流程机械套用至小游戏，也不能以“不收费”推断完全不需要备案。

### 13.3 平台广告与登录边界
- 第一阶段**不接入广告或真实货币付费**；也不引入“看广告获得创业资金”以免破坏平衡经营模型。
- 官方小游戏资料要求包体正确接入TapTap登录，小游戏登录链路可使用`tap.login()`获得短期`code`。如使用`code2Session`取`openid/session_key`，应当由可信服务端进行，不能把`session_key`写入客户端或上传到经营存档。按游戏发布形态和测试环境对接官方登录实现。
- 经营本地模拟排名与TapTap真实玩家排行榜是两套机制；本版本只做模拟企业。**不调用在线排行提交接口**，避免玩家主动重开以后平台成绩仍保留而产生冲突。
- 平台桌面入口/快捷方式能力列在官方小游戏开发指引的“必接能力”栏目中，需在提交前按照当期开发规范确认适配、测试和审核范围；不可为了引导添加而自动创建未经授权的桌面组件。

## 14. 平台API与本地业务接口清单（新增）

### 14.1 必要接入与条件接入

| 用途 | TapTap接口/官方能力 | 第一阶段接入策略 |
|---|---|---|
| 身份 | `tap.login()`、必要时`tap.checkSession()`；受信服务端`code2Session` | 发布联调必须验证；认证过程与经营计算分开 |
| 游戏存档 | `tap.setStorage` / `tap.getStorage` / `tap.removeStorage` | **必接**：本轮经营存档与重开清理，异步操作返回明确结果 |
| 文件系统 | `tap.getFileSystemManager()` | 按正式存档选型使用；不同时引入多套主存档 |
| 页面适配 | `tap.getWindowInfo()`（或官方兼容设备信息接口） | **必接**：竖屏安全区与触摸区域 |
| 网络状态 | 官方网络变化监听/查询能力 | 联调：断网时核心经营仍可运行，在线能力正确降级 |
| 生命周期 | 宿主的前后台切换事件和引擎暂停/恢复事件 | **必接**：切后台时写存档，恢复时一次性计算离线进度 |
| 云存档 | `tap.getCloudSaveManager()`、`deleteArchive`等 | **第一阶段不启用**；如后续启用需处理重开删除与同步冲突 |
| 在线排行 | `tap.getLeaderboardManager()`等 | **第一阶段不启用**，只用模拟企业本地排名 |
| 广告/内购 | TapTap相关广告及支付能力 | **第一阶段不启用** |

实际调用签名、平台版本、权限、回调方式由官方适配文档与真机联调核定；不得把普通Web端API与普通小游戏运行时API混用。为测试方便，PC编辑器可以实现一套仿真适配器，但上线包必须替换为真实TapTap适配。

### 14.2 游戏内部最小接口（非平台官方 API）

```text
createCompany(companyName, initialIndustry, ceoProfile)
rollCompanyNames(industry, count=3)
getOnboardingState()
completeOnboardingStep(stepId)
skipOnboardingTutorial()
replayTutorial()
getCompanyDashboard()
getHireCandidates(departmentId)
hireEmployee(candidateId, departmentId)
getSeverancePreview(employeeId)
fireEmployee(employeeId, confirmed)
createDepartment(departmentType)
setDepartmentStaffing(departmentId, mode, targetCount)
setOperatingPolicy(policy)
advanceSimulation(months, source)
getAnnualReport(year)
getLeaderboard(rankType)  // local bots only
getCloseCompanyPreview()
closeCompany(confirmed, expectedRunId) // destructive, idempotent
getSaveIntegrityStatus()
```

**关键业务校验**：`hireEmployee`不得重复扣费、`fireEmployee`确认前不得扣补偿、`advanceSimulation`不能重复结算月度、`closeCompany`重置中不得提交新员工或自动月结、任意延迟回调不得把旧runId数据写回新公司。
