# 02｜核心数据模型、版本化存档、关闭公司重开

## 2.1 数据设计要求

仅允许**一局活动经营档**；数据按“运行元信息 → 公司/CEO → 员工/部门 → 年度经营与月度滚动摘要 → 事件/排名”组织。采用TypeScript类型+JSON Schema双约束。所有金额以**整数人民币元**储存；倍率和比率用整数基点`bps`（10000=100%）；时间由`gameYear/gameMonth`定义、不得依赖当前手机本地日期进行财务归属。浮点运算仅在临时计算时使用，入账前按统一规则四舍五入到元。

## 2.2 顶层存档类型

```ts
type IndustryId = 'TRADE'|'SOFTWARE'|'SERVICE';
type DeptType = 'BUSINESS'|'HR'|'PROCUREMENT'|'MARKETING'|'CUSTOMER_SERVICE'|'FINANCE';
type Policy = 'STEADY'|'GROWTH'|'PROFIT';
type CashRisk = 'NORMAL'|'WARNING'|'DISTRESS';

type GamePhase = 'CREATING'|'HIRING_INITIAL'|'TUTORIAL_DASHBOARD'|'RUNNING'|'DISTRESS'|'RESETTING';
interface SaveEnvelope {
  schemaVersion: 1;
  gameVersion: string;
  configVersion: string;
  checksum: string;               // 对无checksum的规范序列化数据计算CRC32(8位十六进制)
  revision: number;               // 每次持久成功+1
  runId: string;
  resetGeneration: number;
  payload: GameState;
}
interface GameState {
  phase: GamePhase;
  runId: string;
  seed: number;
  rngCounter: number;
  initializedCapital: boolean;
  gameYear: number;              // 创业=1；完成第1年后切至2
  gameMonth: number;             // 1..12，下一个待结算月
  progressMsInMonth: number;     // 0<= progress< monthDuration
  speed: 0|1|2|5;               // 0暂停
  lastWallClockMs: number;       // 毫秒时间戳，防重领高水位
  lastSettledMonthKey: string|null;  // runId:year:month
  offlineRemainderMs: number;    // 离线不足一个完整月的结算信用
  onboarding: OnboardingState;
  company: Company|null;
  ceo: CEO|null;
  employees: Employee[];
  departments: Department[];
  offers: CandidateOffer[];
  policy: Policy;
  monthlyLedgersRolling: MonthlyLedger[]; // 仅最近24个月
  annualReports: AnnualReport[];          // 完整最多100年，后续归档摘要
  pendingEntries: JournalEntry[];         // 录用等当期支付、月末归属
  eventHistory: EventRecord[];            // 仅最近24条详情，年报保摘要
  botCompanies: BotCompany[];
  consecutiveProfitableYears: number;
  target3YearsAchieved: boolean;
  rescueCapitalUsed: boolean;
  executedCommandIds: string[];          // 滚动最近N条，配合实体唯一ID
}
```

实际所有业务字段以字段字典为准；`save.schema.json`是机器校验基础，后续Agent必须补充其精细定义与版本迁移单测，不能只检查顶层字段存在。

## 2.3 实体字段字典

| Company | `marketDemandIndexBps` | int范围 | 需求累乘变动、存在合理上限 |

### 引用完整性

- 每位 ACTIVE 员工指向一个存在且启用的部门；只有主营部在创建后自动存在。
- 子部门删除功能**不做**；可手动把人数降为0并停用自动招聘。
- `BUSINESS`部门创建后默认`staffingMode=AUTO`，但首次首聘完成前时钟暂停，自动招聘不触发；`company`、`ceo`在CREATING阶段可空；进入RUNNING必须非空、首聘2人、主营部存在。
- `monthKey`包含runId；所有跨run缓存回调一律丢弃。

## 2.4 双槽持久化：不依赖平台的原子多键事务

TapTap缓存`tap.setStorage`可持久化 JSON 可序列化对象；官方单key最大1MB，总缓存10MB，若启用加密单key实际可用约0.7MB，必须为存档留预算。首版推荐单存档目标<500KB，采用摘要截断与滚动历史。**小游戏宿主可能清理本地缓存，MVP不保证跨设备/卸载后恢复；UI和隐私告知不得写“永久云保存”。**

建议键：`ceo/save/a`, `ceo/save/b`, `ceo/save/active`, `ceo/reset/tombstone`。逻辑：

```text
commit(nextState):
  1. validate(nextState) & ensure expectedRunId == currentRunId
  2. produce SaveEnvelope(revision+1, checksum)
  3. write INACTIVE slot; await and readback+verify checksum
  4. write active pointer {slot,revision,runId,resetGeneration}; await
  5. only then update committed-memory and resolve success
```

校验和约定：对除`checksum`字段以外的Envelope进行**对象key字典序排序的规范JSON序列化**，按UTF-8字节计算CRC32（8位小写十六进制）；用于发现意外损坏，**不是防作弊密码学签名**。实现必须提供Node与TapTap同一快照相同CRC结果的单测。

启动恢复：优先有效指针槽；若指针损坏，枚举双槽找到**未被重置墓碑禁止**且校验通过的最高revision；所有候选冲突需明确处理，不能随意恢复过时的旧run。记录、展示`SAVE_CORRUPT`并提供重试/反馈入口，禁止无提示直接覆盖。

若正式实现用单键原子写代替双槽，必须有与上面同级的断电恢复证明，并更新本文件与测试；默认不改变双槽方案。

## 2.5 主动关闭公司事务

```text
UI: 设置→关闭公司→预览失去的数据→二次确认(有效期60秒)
Service:
  acquire exclusive GameMutationLock
  pause clock & invalidate pending timers/auto actions
  assert expectedRunId / confirmationToken
  write reset tombstone {oldRunId, newResetGeneration, resetAt} and await
  clear in-memory old run and inactive slot references
  write empty CREATING state with brand-new runId, fresh RNG seed,
        0 offline watermark and 30万尚未发放标识
  commit new state and replace active pointer
  cleanup old slot safely (cannot resurrect tombstoned run)
  emit ResetCompleted
```

- 重置失败：UI不得显示成功；`tombstone`已存在时重启必须继续清理，**不能继续加载旧run**。
- 如果跨run的`save()`、`settleOffline()`或`hireEmployee()`迟到：检测`expectedRunId`与`resetGeneration`后丢弃。
- 初始化启动资金由`createCompany`以唯一`runId+INITIAL_CAPITAL`凭证记入`paidInCapital`，拒绝任何重复请求。
- **关闭公司不会注销TapTap平台账号**，不会删除依法必须保留的必要认证/运营记录；当前不启用云存档，未来需补云删档或旧云档屏蔽策略。

## 2.6 中途创建与首聘的落盘

阶段：`CREATING`（收集公司、CEO信息）→`HIRING_INITIAL`（已创建公司、首聘0/1/2人）→`TUTORIAL_DASHBOARD`（认识现金/利润/速度）→`RUNNING`。创建后即写存档，前两次首聘通过各自命令立即扣招聘费；**启动资本30万已在公司创建时注入一次**。在正式开始经营前计时暂停，首聘员工首月生效。异常关闭后继续招聘未满人数，不多发资金、不重刷已录用候选。

## 2.7 数据留存与迁移

- 仅保留最近24个月完整`MonthlyLedger`，年度报表最多保留100年；超过100年时压缩较早年份为按10年统计摘要，同时保留创建年份和历史最优成绩。
- 已离职人员不无限保留全字段，最近20条离职摘要足够；全员多时列表虚拟化；候选列表仅保留当前招聘轮次。
- `schemaVersion`每变更必须实现`migrate(vN→vN+1)`，只允许向前，迁移前校验来源、迁移后校验目标，失败不破坏原档。
- 后续如增加云档：以`runId/resetGeneration`决定新旧优先级，**新一轮重开永远不能被旧云档覆盖**。

## 2.8 失败与模拟作弊边界

本地单机小游戏可发生改时钟或改本地存档，MVP不建立反作弊服务器；但应检测时钟大幅回拨、极端异常跳跃，禁止产生**负的离线时长**或无限结算。校验完整性是防损坏不是防外挂安全证明；**虚拟排行榜不会对外声明公平竞技**。
