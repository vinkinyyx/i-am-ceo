# 04｜行业、经济参数与数值平衡 V1

## 4.1 设计原则

第一阶段三种初始行业（电商贸易/软件科技/企业服务），创建后只能经营选定的一种；所有操作流程完全统一。行业只改变订单基数、每员工产能、直接成本率、其他费用率、适用部门价值。任何参数可以在`economy.v1.json`调整，**发布后每个旧存档必须记录生效的configVersion，升级迁移不得隐式重算已结算年份**。

“平衡经营B”不是玩家可选的难度：第一阶段**只有默认平衡难度**，不开发A/C切换。

## 4.4 部门效果量化参数（MVP）

部门配置不做技能树。1名合格员工（skill=60）时的基础效果和上限：

| 部门 | 有效基数 | 1人基准效果 | 总效果上限 | 额外限制 |
|---|---|---:|---:|---|
| HR | 招聘费用＋主营人员可交付产能 | 招聘费减25%；业务产能+6% | 招聘费减40%；产能+12% | 产能提高仅在订单充足时产生新增营收；招聘优惠只影响未来费用 |
| 采购 | 直接成本中的适用采购部分 | 减少10% | 18% | 贸易可采购部分95%，软件10%，服务15% |
| 市场 | 基础潜在订单 | 获客+12% | +25% | 营收不能超过交付产能 |
| 客服 | 售后费用 | 减少35% | 65% | 基准售后费已从其他运营费单列 |
| 财务 | 年固定管理费＋其他可控运营费用（不含售后） | 减少20% | 40% | 不减少工资、直接采购或售后，部门工资另计 |

部门效果需要能力与人数：

```text
qualifiedCapacity = Σ clamp(employee.skill/60, 0.5, 1.5) [仅计算该部门 ACTIVE 员工]
benefitFactor = 1 - exp(-0.85 * qualifiedCapacity)
benefitBps = round(min(maxBenefitBps, baseBenefitBps * benefitFactor / (1-exp(-0.85))))
```

**工程简化替代方案（优先使用）**：为提高跨平台可复现性，用**查表法**取代指数运算：标准员工1人系数100%，2人140%，3人160%，4人170%，5+人175%；平均能力相对60点乘0.5—1.5，再受上限约束。每个部门独立计数，0员工效果严格为0。具体伪码：

```text
staffCount=0 => 0
staffCount>=1 => multiplier from [1.00,1.40,1.60,1.70,1.75]
avgSkillFactor=clamp(avg(skill)/60,0.5,1.5)
effectBps=min(capBps,round(baseBps*multiplier*avgSkillFactor))
```

> **最终实现选择查表法**，HR的两项加成共享同一员工效能倍数，分别受独立上限约束；禁止不同Agent分别使用指数法和查表法导致财务测试不一致。上面的指数表达式只解释边际收益递减概念，非执行算法。配置文件中的`staffMultiplierBps`为唯一来源。

## 4.5 部门收益计算示例

贸易公司某年对外营业额1,600,000元，原始直接成本=960,000元，采购适用比例95%→912,000元；1位专业能力60的采购人员可减10%→91,200元。若工资5,000元/月、招聘费5,000元、设立费10,000元，则设立当年采购部净贡献=91,200−60,000−5,000−10,000=**+16,200元**。

**与旧版V0.9“采购96万全额节约8%”的示例不同**：本版正式计算引入采购适用比例95%、标准员工10%效率，因而例值改变。旧例作为历史教学说明，不可作为V1.0 golden 单测；变更要登记在`11`。

业务尚小的部门可能负贡献：贸易首年72万直接成本43.2万，适用部分41.04万，采购节省4.104万，而人员当年工资6万+招聘费0.5万+设立费1万，总计7.5万，净贡献**−3.396万**；用户不应被强制设立该部门。

### 成本节省预览的统一口径

`当年预计增益 = 可避免费用 + 可实现的新增边际销售贡献 - 新增工资 - 招聘费 - 设部费`。对营销：新增营业额必须受交付产能限制，再乘以行业毛利/贡献率，**不能将新增营业额当作利润**。客服次年留存影响可只显示定性描述，MVP不强制量化并计入今年利润两次。HR的产能价值必须通过有/无HR时的交付能力反事实计算，不得凭空追加固定利润。

## 4.6 人员与策略对平衡的影响

- 自动推荐阈值：新增员工未来12个月预计贡献利润须超过工资和招聘费（STEADY）；GROWTH可略放宽但不可破现金安全线；PROFIT更严格。
- 三种CEO性格只改变成长方向，不在初期额外叠加“创建即+20%收入”，避免三行业首年黄金基准失效。
- 满意度可作为UI简化信息（默认80，只允许少量事件变动），第一阶段招聘对比仍使用`skill/potential/teamwork/personality/salary`；**不另建复杂满意度驱动离职模型**。
- 员工能力年增 `max(1, round(potential/30))`，每年+1~3点，上限100。原始招聘工资不会随成长自动改变，减少早期波动；未来可加年度调薪机制，但不属MVP。

## 4.7 前五年盈利曲线如何产生

**不能手写一张“玩家必定收入上涨”的预设曲线。** 使用可复现的测试种子、稳定员工、经营行为脚本运行60个月，导出：年营收、成本分类、利润、现金、资产、招聘行为、部门效果以及触发事件。测试至少模拟：

1. 无操作：始终2名员工，0支持部门，仅按市场10%增长；收入达到产能上限后趋于稳定，不能凭空继续增长。
2. 理性扩张：在需求明显大于产能时增员，并在经济上合理时选择采购部门。
3. 盲目扩张：第一年开满5个支持部门且招满员，应出现明显成本压力。
4. 保守降本：降低成本但不新增员工，可连续盈利但规模受限。
5. 不利种子：出现订单下降和一次设备损失，玩家仍可通过调整继续经营。

记录五年结果后调整**同一份**`economy.v1.json`，不得修改测试期望以迎合错误结果。`golden-cases.v1.json`只存可解析的基础算术和不变量，5年经营模拟需由实际代码运行生成并保存签名种子。

## 4.8 推荐的平衡验收目标（非玩家硬指标）

- 标准无事件首年可小额盈利：贸易3.8万/软件3.5万/服务4.35万。
- 第一年的人员与部门错误选择可导致亏损，而不是所有开局都赚钱。
- 5年内能够体验至少1次“合理设立部门带来净收益”（可以在贸易业务适当规模时发生），但不保证3个初始行业都要在第3年净赚。
- 同样资金条件下，高能力员工可带来较高产能，高潜力员工在多年后可能超越前者，低工资员工短期现金负担更小；不出现三项完全等价的候选人。
- 只靠点“招聘”不自动增加订单；只有订单限制而不是人手限制时，扩员会增加成本但收入不变。
- 连续3年盈利是目标，不是强制剧情锁；亏损不会立即归零资产/重新创业。

## 4.9 金额边界和可观测指标

单次模拟与对账使用安全整数；若业务数值增长超过`MAX_MONEY_YUAN=100,000,000,000`则钳制并输出可识别状态，不能出现`NaN`, `Infinity`或数字溢出。开发批次M2结束输出平均盈利率、各行业部门使用率、招聘/裁员率、5年平均现金、经营危机触发率；不得私自引入联网遥测。

## 4.10 本地模拟排行榜：可复制实现的bot规则

- 第一轮固定生成12家虚拟企业（可由配置给出安全虚构名称），不是联网玩家；每家记录`botId/name/initialAssetsYuan/initialOperatedYears/baseGrowthBps`。
- 初始总资产范围¥100,000—¥1,500,000、初始已完成经营年数0—8年（按固定种子生成）；排行榜玩家“已经营年数”=**完成的年度数**，刚创立第1年开始时为0，完成第1次年结后为1。
- 每完成玩家1个经营年度，12家bot各推进1年：`newAsset = max(0, round(oldAsset * (10000 + baseGrowthBps + yearJitterBps)/10000))`；基准年增长率3%—12%，`yearJitterBps`从`hash(botId,year)`取[-500,+500]，无额外真实竞争系统。`yearsOperated +=1`。资产上限沿用`MAX_MONEY_YUAN`。
- 排序规则：ASSETS按资产降序、平手经营年限降序、再按稳定ID；TENURE按经营年限降序、平手资产降序、再按稳定ID。排行榜显示排名、数值以及“模拟企业”标识，不引用真实商标。
- 玩家每次主动重开，虚拟企业恢复到**新一轮的同一初始榜单**，玩家资产与经营年限清零。不能保留上一run的历史排位。
- bot不会招聘或实际记账，其资产仅用于游戏内竞争感，**不能与玩家公司的财务数据合并**。
