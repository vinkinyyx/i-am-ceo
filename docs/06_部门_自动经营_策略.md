# 06｜部门创建、业务产能、自动经营、经营策略

## 6.1 部门边界

一个公司始终且仅有一个`BUSINESS`主营业务部。支持部门：`HR`人力、`PROCUREMENT`采购、`MARKETING`市场、`CUSTOMER_SERVICE`客服、`FINANCE`财务；同类型只能创建一次（MVP不重复开若干“采购二部”）。没有子公司、集团共享或跨行业成本分摊。

## 6.2 部门卡片与创建命令

未创建卡：部门名称、图标、作用说明、设立费10,000元、经营适配提示、`创建`按钮。已创建卡：在岗人数、员工工资、当年实际收益、本年度净贡献、自动/手动、`招聘`、`员工列表`。零员工时显示“尚未配置人员：无部门效益”；创建时**不自动送一个员工**。

`createDepartment(type,commandId)`执行：校验当前run存在、非BUSINESS、未创建、现金≥1万元→扣费→记录setup费本年损益和现金→部门创建为`enabled=true,staffingMode=LOCKED,targetCount=0`。玩家随后点招聘或明确启用AUTO。不能创建即开始无上限自动扩员；切为AUTO前应展示预计招聘预算。

部门不能删除，仅可保留空部门、关闭自动招聘；员工可裁员（赔偿仍适用）或调岗（见6.4）。避免“设部门→删除退款→再设”刷钱漏洞。

## 6.3 经营影响顺序

1. 计算已有业务员工的产能；市场部门先影响需求；由两者决定实际营收。
2. 用实际营收乘行业直接成本率、其他运营费率、售后费率，再计算采购、客服等节省。
3. 计算固定管理费以及财务部折扣；HR还可提高主营业务员工产能，但不能突破市场订单上限；招聘折扣只影响当时尚未支付的招聘费。
4. 所有部门员工工资统一扣除一次（每人只属于一个部门）。
5. 新部门设立费、招聘费/裁员费、资产投资另按实际发生时点计入。
6. 部门净贡献 = 可归因节省/可归因销售毛利贡献−该部门工资−相关一次性费用；只能用于**解释**，不能在合并利润上再加一遍。

## 6.4 人员配置（第一阶段最小化）

- 员工属于且仅属于一个部门；UI显示部门人数、目标人数及本年预算。
- 玩家可以直接将部门改为`LOCKED`（不允许自动补员）或`AUTO`（启用自动招聘）。
- **手动调岗**：可选，从员工详情操作，主营业务部↔已建支持部门。调岗下一月生效、无招聘费和裁员赔偿，但不允许员工在两个部门同时计入产能；UI展示迁移后的两边产能/成本变化。若开发精力不足也可移入M3的P1补充，但MVP应至少允许裁员和新部门招聘，不能以调岗为核心依赖。
- `targetCount`为建议人数/手动设定人数；手动减少`targetCount`并不自动裁员。UI必须说明“减少目标不等于裁员”，避免无意触发赔偿。

## 6.5 三种CEO经营方针

| 方针 | 自动招聘门槛 | 现金安全阈值 | UI表述 |
|---|---|---|---|
| STEADY 稳健 | 12月预计新增贡献≥新增12月工资+招聘费 | 至少6个月刚性费用 | 更重视现金和盈利 |
| GROWTH 扩张 | 12月预计新增贡献≥0.8×(工资+招聘费) | 至少6个月刚性费用，不越底线 | 适度提前准备产能 |
| PROFIT 利润优先 | 12月预计新增贡献≥1.2×(工资+招聘费) | 至少9个月刚性费用 | 严格控制新增工资 |

策略不会直接给“固定收入+10%”加成，而是改变可控自动决策；用户随时切换，次次自动招聘决策立即采用新策略，不改写历史账目。首轮不设“自动利润分红”“股票投资”等附加功能。

## 6.6 自动招聘决策算法（保守、可解释）

```text
for month:
  if phase!=RUNNING or cashRisk!=NORMAL: skip
  if annualAutoHireCount>=3: skip
  candidates=[]
  for dept in createdDepts where mode=AUTO:
    derive need by department type:
      BUSINESS: demand > current 12month annualized capacity * 1.10
      SUPPORT: eligible cost/extra demand big enough to cover projected staff cost
    gen 3 candidates by stable RNG; select best predicted net ROI
    reject if projected revenue > delivery cap but dept not solve bottleneck
    reject if not enough cash for fee + reserve (6 or 9 months committed salaries/fixed costs)
    reject if annualRecruitmentBudget exceeded
  choose max positive score; at most one person this month
  issue hire command with deterministic id `autoHire/run/year/month/dept`
  log decision explanations and predicted benefit
```

### 自动选择评分（只用于候选人之间排序）

`score = 0.45*skill + 0.25*potential + 0.15*teamwork + 0.15*(100 - salaryNormalized)`, 其中`salaryNormalized = (salaryMonthly-4000)/4000*100`，各项按0~100计。**最终是否录用由经济ROI约束，而不是单看score。** 不可因刷新候选而重复免费取多个autoOffers。

## 6.7 部门的合理盈亏解释

玩家查看部门卡时显示三项可见值：

- `本年度已节约/新增毛利`：截止当前游戏月真实累计贡献。
- `部门支出`：年度实际工资+建立费+对应招聘费。
- `部门净贡献`：上两项之差（用于决策，不另记入总利润）。

若某部门本年度负贡献，不自动裁员；提示“当前规模尚未覆盖部门工资，建议谨慎扩编”。营销部门新增销售毛利计算须采用同月“实际营收 vs 关闭市场部时在同等条件下的基准营收”的**反事实模拟**，乘对应边际贡献率，不可用所有营业额算贡献。

## 6.8 可解释的经营诊断（只需规则式提示）

优先级：
1. 现金不足 → “暂停非必要开支，可查看人员与部门费用”
2. 市场需求高于产能10%以上 → “主营业务产能不足，考虑招聘/投资”
3. 产能高于需求20%以上 → “人员可能闲置，优先改善获客”
4. 某成本部门连续2年贡献为负 → “部门成本较高，可暂缓招聘或调整人员”
5. 连续3年盈利 → “已实现阶段目标，可继续经营提升资产排名”

一次只展示最重要的一条，点击显示解释数据，**禁止建议玩家执行现金不足的操作**。

## 6.9 测试与可视验证

- 0员工部门节省严格为0；重复建部门不再次扣款。
- 员工岗位调动下一月生效且没有双重工资/双重产能。
- 业务订单不足时增加市场人手可能盈利，业务产能不足时新增市场人手不应让订单无限增加。
- 采购只对行业允许的直接成本部分起效；软件采购不应与贸易同样省钱。
- HR不存在招聘动作时仍可产生受订单限制的产能价值，但不能凭空增加现金；财务优惠不超过固定经营费与其他可控运营费用之和；客服不能扣到售后费负数。
- STEADY/PROFIT/GROWTH的自动录用数有合理差别；但都不得穿透现金安全线。
- 离线同样遵守预算、锁定、禁止自动裁员、禁止自动部门创建。
